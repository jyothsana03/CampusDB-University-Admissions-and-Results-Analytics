# CampusDB: University Admissions and Results Analytics

Problem 01 (Education). A normalised PostgreSQL database for programmes, courses, students, enrolments, exams and
results; SQL analysis of admissions, pass rates and toppers; a Python DB-API notebook with charts; and a MongoDB
model for student activity logs with aggregation pipelines.

## Data source

All data is **synthetic**, generated by `python/gen_data.py` with a fixed random seed (2026), so it is reproducible.
No real students are represented. Names are random combinations of common first and last names.

| Table | Rows |
|---|---|
| department | 4 |
| programme | 6 |
| course | 48 |
| student | 411 |
| enrolment | 2,888 |
| exam | 216 |
| result | 2,888 |
| **Total (PostgreSQL)** | **6,461** |
| MongoDB `student_activity` | 6,995 documents |

How marks are generated: each student has a hidden ability; marks = baseline + 12 x ability + course difficulty + noise,
clipped to 0-100. Entrance score, LMS activity and marks all depend on that ability, which is why they correlate.
These relationships are built into the generator, so read the findings as a demonstration of the analysis, not as
facts about any real university.

## Schema (3NF)

`department` 1:N `programme` 1:N `course` and `student`; `student` and `course` 1:N `enrolment`; `course` 1:N `exam`;
`enrolment` and `exam` 1:N `result`.

Functional dependencies (examples): `course_id -> course_code, title, credits, semester, programme_id`;
`programme_id -> programme_code, programme_name, dept_id, level, seats`; `dept_id -> dept_name`;
`(student_id, course_id) -> enrolment_id`; `(enrolment_id, exam_id) -> marks_obtained`. No non-key column depends on
another non-key column, so there are no transitive dependencies.

**Deliberate denormalisation.** `student.cgpa` is derived data (it can be computed from results and credits). It is kept
for fast reporting and is written **only** by trigger `trg_result_cgpa`, so it cannot drift.

**Triggers**
- `trg_result_validate` (BEFORE INSERT/UPDATE on `result`): the exam must belong to the same course and year as the
  enrolment, and marks may not exceed the exam maximum.
- `trg_result_cgpa` (AFTER INSERT/UPDATE/DELETE on `result`): recomputes the student's CGPA = sum(grade point x credits) / sum(credits).

**Views:** `v_result_detail` (one flat row per result), `v_course_pass_rate` (pass percentage per course).
Grading: 10-point scale (90+ = 10 ... 40-49 = 5, below 40 = fail).

## How to run

Requirements: PostgreSQL 14+, Python 3.10+ with `pandas`, `matplotlib`, `psycopg2-binary`; MongoDB 5+ and `mongosh` for the NoSQL part.

```bash
createdb campusdb
psql -d campusdb -v ON_ERROR_STOP=1 -f sql/schema.sql -f sql/data.sql
psql -d campusdb -f sql/queries.sql

createdb campusdb_py                       # the notebook loads the CSVs into this one
jupyter notebook campusdb_analysis.ipynb   # set PGHOST / PGUSER / PGPASSWORD if needed

python3 python/export_results_for_mongo.py # writes mongo/results_snapshot.jsonl from PostgreSQL
mongoimport --db campusdb --collection student_activity --file mongo/activity_logs.jsonl
mongoimport --db campusdb --collection results --file mongo/results_snapshot.jsonl
mongosh campusdb mongo/campusdb_mongo.js
```

`./run_all.sh` repeats the whole build (regenerate data, load, queries, notebook, charts) using plain `psql`.

## Findings (from the synthetic data)

- Intake rose 47% from 2021 to 2025 (68 to 100 students); M.Sc Data Science grew from 9 to 22, B.Sc Mathematics shrank from 12 to 9.
- Overall pass rate 93.7%; the hardest course is Operating Systems at 86.7%.
- Average CGPA is 8.52 for students with entrance score 80+ and 4.63 for those below 60.
- 58 of 411 students (14.1%) are below the CGPA cut-off of 5.0.
- In the activity logs, pass rate rises from 84.1% (fewer than 6 events in the term) to 100% (12 or more); correlation of activity with final mark is 0.62.

## MongoDB model and indexes

One document per event in `student_activity`:
`{student_id, course_id, course_code, academic_year, event_type: "login" | "assignment_submission", event_ts, details: {...}}`.
Logins carry `device` and `session_minutes`; submissions carry `assignment_no`, `score` and `late`.
Indexes: `{student_id: 1, event_ts: -1}`, `{event_ts: 1}`, `{course_id: 1, academic_year: 1, event_ts: 1}`.
Pipelines: (1) weekly activity per course, (2) engagement band versus exam results through `$lookup`, (3) late-submission rate by programme.

> **Verification status.** The SQL, the Python and the notebook were executed against PostgreSQL 16. The MongoDB
> scripts were **not** executed against a live MongoDB server (none was available in the build environment). The
> expected output of the pipelines was reproduced in pandas on the same data (`python/verify_mongo_pipelines.py`,
> `outputs/mongo_expected.txt`); run `mongo/campusdb_mongo.js` to compare.
>
> In the build environment `psycopg2` was not installed, so the notebook fell back to `python/psql_dbapi_shim.py`, a small
> DB-API wrapper around `psql`. With `psycopg2` installed the notebook uses it directly.

## SQL vs NoSQL: short comparison

| | PostgreSQL (relational) | MongoDB (document) |
|---|---|---|
| Schema | Fixed, enforced by the database | Flexible; optional validator |
| Integrity | PK, FK, CHECK, UNIQUE, triggers | Application-level; no foreign keys |
| Relationships | Normalised tables joined with JOIN | Embedded documents or `$lookup` |
| Strength here | Marks, CGPA and reports that must be exactly right | Event logs with different shapes, written in bulk |
| Weakness here | Adding a new event type means altering a table | Cross-collection joins are slower and clumsier |
| Query language | SQL | Aggregation pipeline |

Choice made: results, grades and CGPA stay in PostgreSQL because correctness and constraints matter; activity logs go
to MongoDB because logins and submissions have different fields and arrive as a stream.
